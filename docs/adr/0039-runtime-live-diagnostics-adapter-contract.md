# ADR 0039 NTK Runtime ライブ診断画面のアダプタ契約

## 状態と適用範囲

2026年11月27日のユーザー指示に基づく仕様案。アダプタ開発者が診断画面へ渡す情報を準備し、適合を確認するための契約を定める。画面の描画と配信は診断側で行い、Runtimeの追加負荷を抑える。以下の契約ID、形式、具体値、受入条件は本案で定義する。2026年11月28日にv1.12.0への配分と標準化方針を採用した。親[#175](https://github.com/Tao-pyth/nymph-toolkit/issues/175)、設計[#180](https://github.com/Tao-pyth/nymph-toolkit/issues/180)、実装[#181](https://github.com/Tao-pyth/nymph-toolkit/issues/181)、負荷と受入[#182](https://github.com/Tao-pyth/nymph-toolkit/issues/182)。以下の検証結果と適用版は公開後確認を経て確定する。

2026年11月27日段階の成果物は仕様書。既存アダプタの改修は各アダプタの対応時に扱う。診断向けの報告を実装していないアダプタは、公開済みの登録・配置・稼働情報のうち取得できる項目で表示する。天気情報の取得・処理は別途アダプタ等が担当し、この契約ではその表示用出力を受け取る。天気を使う受入試験は固定のサンプルデータで実施する。

## 報告の登録と送信

起動設定で報告を有効にするアダプタの `module_id`、受信先ID、一意な受信口ID `slot` を登録する。ランチャーは起動ごとに、ハイフンなしの32文字の小文字16進文字列 `run_id` を発行する。`slot` は `[a-z][a-z0-9_-]{0,31}` に一致する。ランチャーは `run_id`、受信先ID、`slot` を当該アダプタの診断設定に渡す。

任意の診断契約は、受信口ごとに `ContractKey("ntk.diagnostics.report." + slot, "1")` を使い、非同期操作 `publish(report)` を提供する。受け口は、登録した受信口に対応する `module_id` を基準に報告を照合する。アダプタは起動設定で指定された相手へ、既存のCoreが許可する接続で報告する。入出力はJSON互換値で、配置が `LOCAL` と `PROCESS` のどちらでも同じ意味を持つ。診断報告により、稼働判定や接続先の選定、活動の判断を変えない。 [直接通信の方針](0015-core-authorized-direct-communication.md)・[v1 Core接続契約](0026-v1.0-core-connection-contracts.md)

### 報告オブジェクト

1件の報告は、そのアダプタがいま公開する診断情報全体を表す。以降の表で「任意」としたキーは省略できる。各オブジェクトのキーは表に記載したものを使用する。新しい項目を加える場合は契約版を更新する。

| キー | 型と制約 | 意味 |
|---|---|---|
| `version` | 整数 `1` | 報告形式の版 |
| `module_id` | 文字列 | 起動設定で登録されたアダプタIDと完全一致 |
| `run_id` | 文字列 | ランチャーから受け取った今回の起動ID |
| `sequence` | 正の整数 | 起動IDとアダプタの組で1から始める報告番号 |
| `reported_at` | UTC時刻 | アダプタが報告を組み立てた時刻 |
| `condition` | オブジェクト、任意 | アダプタ固有のコンディション |
| `processing` | オブジェクト、任意 | アダプタ全体の処理状況 |
| `resources` | オブジェクト配列、最大16件 | アダプタが所有する資源の使用量 |
| `outputs` | オブジェクト配列、最大16件 | 表示用の業務出力 |

時刻は `YYYY-MM-DDTHH:MM:SS.sssZ` 形式とする。整数の絶対値の上限は `9007199254740991`。整数に真偽値は含めず、実数は有限値とする。配列内の各IDは `[a-z][a-z0-9_-]{0,63}` に一致し、同じ配列内で一意とする。表示名・説明・単位・出典は空白だけの値を避け、80文字以内のプレーンテキストとする。本文に相当する `content` のテキスト値と項目表の文字列値は1,024文字以内とする。報告単体を余分な空白を付けずUTF-8のJSONに直した大きさは16,384バイト以下とする。計測には `json.dumps(report, ensure_ascii=False, allow_nan=False, separators=(",", ":")).encode("utf-8")` を使える。通信フレーム側には別途既存の上限が適用される。

### 状態と資源

| オブジェクト | キー | 値 |
|---|---|---|
| `condition` | `level`、`label` | `info`、`warning`、`error` のいずれかと、アダプタが選ぶ表示名 |
| `processing` | `accepting`、`active`、`capacity` | 受付可否の真偽値と、処理中件数・同時処理上限の非負整数。上限が報告できない場合は `capacity` を省略 |
| `resources[]` | `id`、`label`、`kind`、`unit`、`used`、`limit` | 種別 `disk` または `memory`、単位 `bytes` または `items`、使用量の非負整数。同じ単位の正の上限値 `limit` は任意 |

処理状況が省略された場合は取得済みの公開 `Usage` を使う。受付可否と処理枠の空きは別に示し、`active >= capacity` は空き枠なしとして表示する。資源の `limit` が省略された場合は使用量だけを表示する。上限超過時は実測値を保持し、上限超過を明示する。状態未報告と0件を区別する。他機能へ保存を依頼する場合、他機能が所有するストレージ使用量を当該アダプタの値へ算入しない。

### 出力

`outputs[]` の共通キーは `id`、`label`、`kind`、`observed_at`、`content`。任意キーは `source` と `expires_at`。外部取得情報では提供側が両方を指定し、`expires_at` を指定する場合は `observed_at` より後とする。受け口は取得種別を推測せず、指定された項目を検証する。アダプタが外部データから表示項目を選び、`source` に出典名を設定する。有効期限を過ぎた出力は、次の報告を待たず期限切れと表示する。

| `kind` | `content` の形式 | 画面での扱い |
|---|---|---|
| `text` | 文字列 | テキストカード |
| `items` | 1〜32件の `{label, value, unit?}`。値は文字列、有限数、真偽値のいずれか | 項目表またはカード |
| `series` | `{unit, points}`。点は1〜120件の `{at, value}` で、時刻の昇順かつ重複なし。値は有限数 | 時刻と単位を付けた折れ線。点が1件なら値を表示 |

表示用データの選別は提供側の責務とする。許可範囲は表示に必要な集計・項目に絞り、資格情報、音声、文字起こし、文書原文、業務パラメータ、例外本文を通常の診断報告に含めない。画面は文字列をテキストとして表示する。

### 報告例

天気を提供する機能が取得済みの値をまとめた例。受信口IDが `weather` の場合、`ntk.diagnostics.report.weather/1` の `publish` に次のオブジェクトを渡す。

```json
{
  "version": 1,
  "module_id": "weather",
  "run_id": "4e52faf504ad447da6e37f0915ce90a1",
  "sequence": 4,
  "reported_at": "2026-11-27T05:32:10.000Z",
  "condition": {"level": "info", "label": "最新の予報を取得済み"},
  "processing": {"accepting": true, "active": 0, "capacity": 1},
  "resources": [],
  "outputs": [
    {
      "id": "forecast",
      "label": "天気情報",
      "kind": "items",
      "observed_at": "2026-11-27T05:32:04.000Z",
      "source": "試験用の天気データ",
      "expires_at": "2026-11-27T05:47:04.000Z",
      "content": [
        {"label": "地域", "value": "東京"},
        {"label": "気温", "value": 21, "unit": "°C"},
        {"label": "予報", "value": "晴れ時々くもり"}
      ]
    }
  ]
}
```

## 更新・失敗・負荷

1. アダプタは有効化後の初回と、公開する状態・使用量・出力が変わったときに報告する。`sequence` と `reported_at` だけの変化では送らない。前回送信開始から単調時計で1,000 ms以上空ける。それまでに変化が重なった場合は保留1件を最新値へ置き換える。各アダプタの送信中は1件までとし、業務処理は送信や画面の更新を待たない。
2. 受け口は登録、形式・大きさ、起動IDと報告番号の順に確認し、受理した報告で前の報告全体を置き換える。省略された任意項目や配列から外れたIDは、その報告で公開終了とする。`sequence` が前回受理値以下なら無視し、欠番の補完は待たない。送信時刻で順序を決めない。起動IDが変わったら旧起動の報告を現在値から外す。
3. `publish` の応答は `{"status":"accepted","sequence":N}` または `{"status":"invalid_report"}`、`{"status":"stale_report"}`、`{"status":"not_available"}` のいずれか。旧起動、重複、逆順は `stale_report`。受信口が無効な場合は `not_available`。形式違反と、受信口に割り当てられた `module_id` との不一致は `invalid_report`。拒否で最後の有効値と受理番号を更新しない。`accepted` は診断用メモリへの受付を表す。表示・保存の完了は別である。
4. 応答の期限切れや結果不明では同じ報告を再送しない。次に新しい観測があれば、その時点で用意できる最新の報告を次の番号で送る。診断プロセスの停止や配信の滞りは受け口で吸収し、外部の画面やプロセスを待たずに受付結果を返す。Coreの接続自体で障害が発生した場合は既存の連携エラー契約に従う。 [Connectionsの失敗と中断](../connections.md)

画面に必要なRuntime情報は、初期状態と既存の状態変化から取得する。診断側で通知キューを消費したり、定期ヘルス申請やアダプタへの定期照会を行ったりしない。親Runtime側に置く通常の報告枠は登録アダプタにつき最新1件。到着が集中しても、診断プロセスへは1秒ごとに変更があったアダプタの最新値だけを渡す。診断プロセスが状態変化を直近200件まで保持し、ブラウザーへ初回スナップショットとその後の差分を配信する。異常終了、Runtimeの確定終端、子の後処理未確認は通常の更新枠とは別に、起動中は対象ごとの最新値を保持する。通常のCore履歴保存とは独立した仕組みとする。

診断プロセスの配信・集約はランチャーが管理し、Coreの機能用子プロセスの監視対象から外す。ブラウザーは構成図、活動の予定と実績の時間軸、使用量バー、出力カードを描画する。対象Runtimeのイベントループで1秒ごとに観測の心拍を更新する。確定終端に達する前に3秒間心拍が届かなければ、最後の値を残して「観測更新停止」と表示する。アダプタの出力期限、観測更新停止、Runtimeの確定終端を個別に示す。画面のタブ数に応じて収集や報告を増やさない。

## 簡易コンソール

起動設定でアダプタごとに表示名、操作ID、固定の接続先と公開契約ID・版、操作名、入力項目、画面に渡す応答項目を指定する。入力型は文字列、整数、有限数、真偽値。未登録のコンソールは表示しない。登録された操作はフォームまたはボタンで明示実行し、既存の呼び出し経路を使う。アダプタの元の入力検証と操作契約も適用する。

画面の自動更新はコンソール操作を起動しない。操作ごとに受付、完了、業務エラー、結果不明を区別し、結果不明で自動再送しない。既存の結果照会がある場合は別の明示操作として設定できる。初版の受入用デモで公開する操作は副作用のない状態照会とする。

## 受入試験

同じ試験用アダプタと受け口で、各ケースの入力、受付応答、表示値を照合する。時刻と配信競合は制御時計または同期点で再現する。

| ID | 実施条件と期待結果 |
|---|---|
| LD-01 | 同一の正常報告を `LOCAL` と `PROCESS` で送る。UTF-8の日本語、0件、数値・単位、項目表、系列の表示が一致する。診断未対応アダプタも基本状態を確認でき、未報告項目は0と表示されない。 |
| LD-02 | 受理済みの有効報告に続けて、形式の版違い、重複ID、負の使用量、真偽値の件数、非有限数、順序違反の系列、無効な時刻、期限関係の違反を与える。形式違反は報告全体を拒否し、表示中の有効値を保持する。16,384バイトは受理可能で、16,385バイトは形式違反になることをUTF-8のバイト数で確認する。 |
| LD-03 | 正しい受信口に報告番号1、3、2、3、4を送る。1・3・4だけを受理する。再起動後に旧起動の高い番号を送っても新起動の1を置き換えない。受信口と一致しないアダプタIDを入れた報告は、どちらの公開値も変更しない。 |
| LD-04 | 連続変更と遅い受信を与える。送信中1件と保留の最新1件の範囲で推移し、送信開始間隔は1,000 msを下回らず、最終観測値が反映される。到着が集中しても直近の受理値だけが次の差分に残る。取り消した報告と結果不明になった報告は再送されない。 |
| LD-05 | 有効な出力の直後にIDを除いた報告、状態を省略した報告、期限直前と期限到達時を与える。出力撤回、基本状態への復帰、期限切れを区別する。画面の読み直し後も現在の公開項目だけが表示される。 |
| LD-06 | 通常の予定到達、接続確認中と失効、子の異常終了と後処理未確認を実Runtimeで発生させる。画面だけ停止した場合は業務が続くこと、Runtimeの心拍が止まった場合は観測更新停止になること、確定終端後も失敗の記録を確認できることを照合する。 |
| LD-07 | 公開・許可済みの照会、許可外操作、不正入力、結果不明、再読み込みを試す。許可済みの明示操作だけが呼ばれ、応答は許可済みの項目だけ表示される。未知の結果で呼び出し回数は増えない。 |
| LD-08 | 画面の図・グラフ・状態ラベルを照合する。アダプタ選択、履歴絞り込み、コンソール操作をキーボードで行え、狭い画面でも時刻・単位・状態を確認できる。色を除いても通常・確認中・失効・異常を区別できる。 |
| LD-09 | 診断無効、有効1タブ、有効3タブで次項の負荷比較を行う。イベント収集頻度と報告数はタブ数によって増えず、診断キューの保持量は報告の上限内に収まる。 |

### 負荷比較の合格基準

WindowsとLinuxで、同一マシン・Python・Core設定ごとに比較する。[既存のハイブリッド負荷手順](../validation/v0.8.md)を基に、4配置を同じ業務RPC・活動・転送条件で動かし、30秒のウォームアップ後に5分測定する。各条件を3回実施して順番を入れ替え、反復ごとの値と3回の中央値、親RuntimeのCPU時間・RSS、報告数、キューの最大保持量を記録する。診断有効時には各配置で報告上限に合わせた変更を与える。業務RPCのp95は同じ測定区間と同じ集計方法で比較し、サンプリング窓を使った場合は窓長を記録する。

受入の初期基準は、診断無効を基準として、各配置の業務RPCのp95増加が `max(基準値の5%, 0.25 ms)` 以内、業務RPCの完了件数毎秒の低下が5%以内。診断有効の1タブと3タブの両条件で満たす。診断プロセスを終了させても業務が継続し、通常のCore履歴受付と保存の契約を維持する。短いCIの統合試験はこの比較測定と別に記録する。

実装着手前に、適用マイルストーン、親Issue、対応単位の子Issueを確定し、採用した版・具体値を記録する。適合結果にはケースID、対象コミット、OS・Python・配置、使用したデータ、実測値、未検証範囲を残す。 [Issue運用](../issue-workflow.md)

## v1.12の初版と標準適用

起動時に明示有効化し、診断配信はローカルループバックに限定する。親Runtime内の報告受信モジュールから、ランチャー所有の別プロセスへ表示用スナップショットと差分を渡す。既存の履歴イベントから許可した項目のみ投影し、履歴受付と保存、通常の通知キュー、機能用子の監視を維持する。許可済みで副作用のない状態照会を簡易コンソールの初版の対象とする。

対象機能の新設・関連改修に契約を適用し、現行アダプタには基本表示の経路がある。標準の発効と適合結果は公開後確認[#183](https://github.com/Tao-pyth/nymph-toolkit/issues/183)で記録する。

アダプタは起動時に `DiagnosticSession.report_settings(slot)` の設定を受け取り、開始後に `ReportPublisher` を作成する。変更時に `update`、停止時に `close` を呼ぶ。ランチャーは `DiagnosticSession.start()` のURLを利用し、Runtimeの終了結果を表示後に `close()` で診断プロセスを回収する。診断スロットは最大64。初回と以降の差分をブラウザーから取得し、タブ数はRuntime側の収集頻度に影響しない。簡易コンソールは `ConsoleQuery` で副作用のない既存操作・引数型・表示項目を固定する。
