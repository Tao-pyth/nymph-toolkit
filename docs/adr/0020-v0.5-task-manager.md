# ADR 0020 v0.5のTaskManager基本機能と活動判断の境界

## 状態

一部採用・設計中。2026年11月21日のR17「v0,5目指して作業をお願いします」と、その後の一問一答を根拠にする。[親Issue #5](https://github.com/Tao-pyth/nymph-toolkit/issues/5)、[設計子Issue #45](https://github.com/Tao-pyth/nymph-toolkit/issues/45)、[v0.5.0マイルストーン](https://github.com/Tao-pyth/nymph-toolkit/milestone/5)で追跡する。

ユーザーの回答で採用した事項、今回の実装上の判断、未決の提案を分ける。v0.5への着手指示と子Issueの登録を、全ての設計案の採用や実装完了と扱わない。現時点でTaskManagerの製品コードは未実装、A05は未検証、v0.5.0は未公開である。

[ADR 0004](0004-activity-authority.md)の責務境界を具体化する。Runtime・Registry・ModuleGroup・Connections・FileStoreの採用済み契約を置換せず、[ADR 0019](0019-v0.4-connections.md)を前提とする。

## 背景と実施範囲

v0.4.0で接続管理と非同期履歴保存まで公開・検証済み。v0.5では、ダミーNymphが決めた活動内容、開始時刻、期間と、Coreが観測した実行状態を対応付ける。Nymphの判断アルゴリズム、本番Subsystem・Adapter、IPC、PC全体の状況取得、個体データの複製・移植・伝播は追加しない。

CPython 3.12以上、CoreとContractsの単一配布パッケージ、asyncioによる同一プロセスの協調的実行を維持する。将来の活動変更・優先度・中断再開はv0.6の判断対象である。v0.5でNymphの指示を実行するために必要な最小操作と、その範囲の理由は実装前に本ADRへ記録する。

## D1 予定時間の到達と判断主体（ユーザー回答により採用）

質問では「22時開始・2時間」と指定され、実際には22時10分に開始した例を示した。期間の起点をCoreが一方的に決める問いに対し、ユーザーは「それは24時時点でNimphが判断すること」と回答した。続く確認で「通知して活動を継続し、Nymphの指示を待つ」を選択した。表記は既存のプロジェクト名に合わせてNymphとする。

採用内容は以下のとおり。

- 指定開始22時・期間2時間なら、予定上の到達時点は翌0時であり、実開始が遅れたことだけでCoreが翌0時10分へ延長しない。
- 到達時点でCoreはNymphへ通知する。活動が継続中なら、通知後も継続してNymphの指示を待つ。
- 到達だけを理由とする自動終了、自動中断、自動延長は行わない。終了・継続・延長等の活動判断はNymphが担う。
- 「期間」は、Coreが強制終了する実行タイムアウトと同一ではない。実際に始まった時刻、経過した時間、終わった結果は予定と分けて観測する。
- Core全体の停止・保存回復不能時の終了・既存の接続中断契約は別の実行管理上の事象である。予定時間の到達をそれらの障害・停止処理に置き換えない。

最初の質問にあった「実開始から2時間を確保する」「指定開始から2時間で自動終了する」という解釈を採用記録へ含めない。今回の回答は、活動を停止する時間予算の採用ではなく、予定到達時にNymphが判断する境界を具体化したものである。

### D1の受入シナリオ

ダミーの予定時刻22時、期間2時間、実開始22時10分を制御可能な時計で再現する。翌0時に到達通知があり、その通知だけでは活動が終了・中断せず、予定時刻も自動で延長されないことを確認する。Nymph役からの後続指示と、活動の実結果・後処理完了を区別して追跡する。活動名を「調査」「睡眠」へ変えてもCoreの規則を変えない。

## D2 再起動時の活動（要決定）

接続設定の復元はADR 0019で採用済み。活動の予定・途中状態の復元は別の判断であり、その契約を流用しない。

現在、以下の方針をユーザーへ一問一答で確認している。

1. 履歴をNymphへ渡し、再登録・再開はNymphが判断する。
2. 未開始の予定は自動復元し、実行途中の活動はNymphが判断する。

回答前に活動の自動復元・再実行や、その不採用を確定しない。履歴読出しを採用する場合は、未保存分、不完全な最終記録、保持期間を過ぎた退避先の扱いも具体化する。活動履歴の参照を個体データの複製・移植機能と混同しない。

## 実装前に具体化する事項

以下は判断対象であり、採用済み仕様の一覧ではない。D1の採用境界を守って具体化する。

| 論点 | 判断と検証の対象 |
|---|---|
| 入力と時刻 | 活動ID・要求元・内容、時刻の型とタイムゾーン、期間の型・不正値、既に過ぎた開始時刻 |
| 計時 | 予定到達時刻、実開始、待機時間、実行中の経過時間とCPU時間の区別、壁時計の補正 |
| 通知 | 到達・実開始・早期完了・失敗をNymphが取得する入口、重複と終了後の通知、指示との競合 |
| 実行 | 活動の実行入口・所有者、接続の準備待ちとの境界、通常失敗・連携エラー、同時実行 |
| Nymphの指示 | 基本機能で必要な終了指示と後処理、v0.6の変更・取消・中断再開との配分 |
| 状態と結果 | 未開始・実行中・終了要求中・終了済みの区別、失敗保持、変更不能な観測値 |
| 停止と中断 | Runtime停止、初期化失敗、協調的中断時の活動との関係、残存タスク・後処理 |
| 保存 | 活動の入力・状態変化・通知・結果の履歴、既存FileStoreの救命・未保存報告との整合、D2の採用範囲 |

公開API・内部実装上の選択は実施指示の下で判断し、過去にユーザーがその名前・型・数値を採用していたという書き方をしない。利用者の意図を変える未決事項は一問一答で確認し、依存する実装を先行しない。

## 影響・検証方針

予定時間到達の通知と実際の活動終了を別に扱うため、単にasyncioのタイムアウトで活動を取り消す実装はD1を満たさない。CoreはNymphに判断材料を返し、意思決定結果として届く指示を採用契約に従って実行する。

A05では予定と実際の開始・結果、到達後の継続、早期完了・失敗、Runtime停止時の後処理、採用した再起動動作をダミーで確認する。保存障害・連携エラーの検証では、既存の中断・受付停止・救命を維持する。既存129テストの回帰、実行例、配布物からのテスト、対応Python版とWindows/LinuxのCIを行う計画である。現時点の合格実績としては扱わない。

v0.4.0までの公開タグ・Release添付を保持し、v0.5の進捗は未リリースの文書・Issueへ記録する。
