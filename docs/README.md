初稿作成時の環境では `read_thread` が利用できず、元会話全文との照合は未実施である。確定事項の記述はR2・R3の明示指示を根拠にし、R4で責務境界の説明と判断対象を補う。R4のレビュー本文が述べる過去の経緯と、元会話の直接確認は確認範囲を区別する。既存稿だけにある断定は根拠として採用しない。原文確認後に追加する場合は、発言と採用状況を照合してからADRへ記録する。

R5は今回の明示的な編集根拠として扱う。v1.0.0で接続契約を大きく形作る目標は確定事項として追加する。契約詳細、Subsystem・Adapterの正式名称・実装順序・機能配分、奇数・偶数マイナーとパッチの運用は提案・要決定として記録する。R5が指定した研究方針と責務境界を各提案の前提にする。

R6の配布方針はADR 0009で採用として記録する。前段で提示されたフォルダ構成案のうち、将来の個別パッケージ名や分割対象、Capability照合の担当などは引き続き具体化する事項として扱う。

R7の最終ビジョンはvisionに収録し、ADR 0010で長期ビジョンとして採用する。元の本文にある具体的な構想は長期目標として位置付け、現行バージョンへの割当や受入条件は後続判断へ残す。本文には現在の通信方針、ロードマップの採用状態、公開準備の状態を補って既存資料と整合させる。

R8によりApache-2.0を採用し、ADR 0011に適用範囲を記録する。R7反映時点では未決だったライセンス選定は解消済みである。第三者成果物と個体データの条件、公開先・公開範囲の判断は別途扱う。

R9により公開先を個人アカウント `Tao-pyth`、公開範囲をpublicへ確定し、ADR 0012へ記録する。公開の判断と作業の完了は区別し、実際の状態はreleaseで管理する。

R10の着手前ルールはADR 0013へ採用として記録する。既存の各段階をマイルストーンと親Issueへ展開し、コード変更は対応単位の子Issueを登録してから行う。課題への登録を仕様採用と混同しない。

R11に伴うv0.2のPython・配布・Runtimeの実装判断はADR 0014に記録する。残りのバージョンの機能配分案や通信緩和案を採用する指示ではない。

R12による後続判断で直接通信の緩和を採用し、ADR 0015へ記録する。ADR 0003のCore経由のみという旧判断は履歴として保持する。Coreが管理・許可した経路での直接通信とCore経由の通信を認め、具体的な許可範囲・接続契約は実装前に判断する。採用判断と通信機能の実装状況を区別する。

R13に伴うv0.3の登録・依存・着脱・Runtime連携の判断はADR 0016に記録する。v0.4以降の通信契約・活動管理・IPCや本番Subsystem・Adapterを先行採用する指示とは扱わない。

R14の接続管理方針は[ADR 0017](adr/0017-connection-binding-and-health.md)へ採用として記録した。この時点で未決だった選定担当、永続化、互換性、ヘルスチェック・中断の範囲は、後続のR15・ADR 0018で具体化する。前のアシスタント回答にある毎回の許可証検証は未採用の提案であり、必須要件にしない。方針の採用とConnectionsの実装を区別する。

R14追補として、失効はエラー回避を目的とし、「参照して欲しくないのに参照する」状況を想定しないというユーザーの説明を記録する。ADR 0017・受入案にあった利用停止の検討を、協調する機能間の記録・通知・処理の整合へ明確化し、強制的な参照遮断を実装要件にしない。

R15の最終回答は[ADR 0018](adr/0018-connection-selection-health-and-recovery.md)のD1〜D7へ記録する。候補選定の途中回答より後の訂正を優先し、Coreに条件関数を渡す案は採用しない。容量不足への即時応答とヘルス確認中の期限付き待機、元の失敗処理とその後の新規要求、接続設定と現在の稼働状態の復元を区別する。履歴の退避はCoreの運用上の救命措置であり、Nymphの個体データの複製・移植を採用したものではない。

資料作成者が提示したJSON/JSON Lines、接続の識別キー、初回要求の競合規則、バッファ件数・書込間隔等は0018の実装提案として分離する。具体的な公開API・設定値等は未決。R15への回答と資料反映指示の確認範囲を根拠とし、取得していない元会話の全文を照合済みとは扱わない。

## 状態の読み方

R16のv0.4作業は[ADR 0019](adr/0019-v0.4-connections.md)で段階的に具体化する。#37〜#44を親Issue #4・v0.4.0配下へ先に登録した。API・保存等の実装判断は採用した節と未決の節を分け、方針・実装・受入・公開をそれぞれ記録する。

R17のv0.5作業は[ADR 0020](adr/0020-v0.5-task-manager.md)へ記録する。#45〜#51を親Issue #5・v0.5.0配下へコード変更前に登録した。D1〜D4はユーザー回答、D5〜D8は今回の実装判断である。最初の期間起点の選択肢を採用したことにしない。再起動時の自動再実行を追加せず、履歴をNymphへ渡す。実装の進捗とA05全体の完了は[検証記録](validation/v0.5.md)で分けて扱う。

計画の整備を依頼されたことと、計画内の製品仕様案が採用されたことは、それぞれ状態を記録する。v0.2はR11・ADR 0014、v0.3はR13・ADR 0016、v0.4はR16・ADR 0019で具体化した。v0.5はR17・ADR 0020で採用範囲を具体化した。後続の未決部分を実装仕様として扱わない。v0.6はR18・ADR 0021で範囲・詳細契約・受入条件を設計採用した。D1・D2の個別回答とD3〜D10の委任に基づく判断、実装の完了と最終受入・公開を区別し、[v0.6受入記録](validation/v0.6.md)に証拠を残す。v0.7〜v0.8への機能配分はR18時点では提案であり、R19・ADR 0022で開発計画として採用した。

R4で列挙された時間・優先度の変更、中断・再開、取消・終了は採否を判断する対象として追記する。Subsystemの機能的依存と独立性の整理案のうち、v0.3の採用範囲はR13・ADR 0016で具体化した。Coreが扱う機械的な実行順序と、Nymphが決める活動の価値・優先度の境界を明示し、優先度機能とその作用、任意実行枠はR18・ADR 0021で設計採用した。過去の採否検討と、その後の採用判断を区別する。

既存のV0.1〜V0.9という表記はv0.1.0〜v0.9.0の節目を指す。v1.xの名称・配分の変更時には、roadmap、architecture、関連ADR、acceptance、releaseと単一配布用引継ぎ書を照合する。

2026年11月21日のR19を[ADR 0022](adr/0022-v0.7-v0.9-hybrid-and-completion.md)に記録する。1〜18の個別回答と19〜64の明示一括採用を区別し、全64項目をA07〜A09へ対応付ける。v0.7〜v0.8の機能配分はこの後続判断で開発計画として採用し、理由を記録した再配分を認める。前節の提案・未決という記述はR18以前の判断範囲を示す。v1.xの名称・順序・配分案は今回採用しない。

設計子Issue [#60](https://github.com/Tao-pyth/nymph-toolkit/issues/60)を親#7・マイルストーンv0.7.0配下へ登録し、引継ぎ書生成ヘッダー変更前にGitHubの親子関係を確認した。API名・型・フレーム・具体的設定値などの実装詳細は後続の対応単位で記録し、採用済みの64項目を再質問しない。これはR19時点の状態である。R20によるv0.7の実装・A07確認は[検証記録](validation/v0.7.md)で追跡し、A08・A09は未完了である。

## 文書の更新

判断履歴は個別ADR、実装状況はルートREADME、実装手順と検証条件は各Docsで管理する。矛盾を見つけた場合は根拠表と後続の採用記録を確認し、関係する文書を同じ変更で整合させる。

単一配布用の引継ぎ書は、ルートREADME、CONTRIBUTING、AGENTS、本書、vision、architecture、runtime、registry、connections、task-manager、hybrid、ADR索引と各ADR、roadmap、acceptance、validation配下の記録、development、issue-workflow、release、CHANGELOG、LICENSEの順に全文を収録する。再作成時はMarkdown文書の見出しを一段下げ、ローカルリンクを表示名とリポジトリ直下からのパス表記へ展開する。LICENSEは原文を変更せずtextコードブロックに収録する。収録元のファイル名を各章に付ける。

Python 3.12以上で `python tools/build_handoff.py` を実行して再生成し、`python tools/check_docs.py` で本文一致・ローカルリンク・文字コード・改行・LICENSEを確認する。[再生成ツール](../tools/build_handoff.py)と[文書確認ツール](../tools/check_docs.py)はCIでも使用する。

リポジトリ内の引継ぎ書は最新の資料へ同期し、公開済みReleaseの添付とタグはその時点のスナップショットとして保持する。v0.1.0以降の更新内容はCHANGELOGの未リリース欄で区別する。
